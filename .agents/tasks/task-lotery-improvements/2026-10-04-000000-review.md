## High-level view

The central behavioral problem fixed here is index misalignment between the feature matrix and the target vector. Both `main.py` and `prediction.py` were using `.tail(len(X))` to align targets after `dropna()`, which silently mismatches rows when NaN removal is non-contiguous. The `.loc[X_df.index]` fix eliminates that silent corruption.

The fixed-category series encoding (`pd.Categorical(..., categories=settings.SIGNOS)`) is now consistent across training and prediction. Previously the free `.astype("category").cat.codes` encoding could produce different integer-to-zodiac-sign mappings depending on which signs appeared in a given dataset slice, making model outputs non-reproducible across runs. The `sign_mapping` key added to the saved model payload means consuming code can now decode predictions without depending on dataset order.

The `sincronizar` flag on `ejecutar_entrenamiento` eliminates the double-sync when the pipeline calls training after a prior sync step. This is a clean fix — the default stays `True` so direct invocations of `--entrenar` still sync, and only the pipeline passes `False`.

The chronological split in `_evaluar_individuo` replaces random shuffling, which was the right call for a time-series use case. Evaluation now tests on the most recent 20% of data rather than a random mix, which gives a much more realistic accuracy signal. The baseline accuracy log added alongside it contextualizes the model score against majority-class frequency, surfacing models that barely beat random.

The Docker section in `README.md` diverges from the plan's service names (`lottery-system` / `lottery-scheduler`) and from what a real `docker-compose.yml` in this repo would define — there is no `docker-compose.yml` in the project. The examples use `sync` and `prediction` instead. This is documentation-only and doesn't break runtime behavior, but the service names will need updating when a compose file is added.

The fixup commit (`1a8aec8`) was not part of the plan. It restores `excel_updater.py`, which had been truncated (the base branch version ended mid-file with no newline). The restored version adds `actualizar_excel_incremental()` using `SuperAstroScraper` — the same scraper that was removed from `main.py`'s import in T14. The new function uses `settings.LOTTERIES` and `settings.CLAVES_UNICAS`, which aligns with the plan's intent.

3. **`baseline_result` approximation via `y_result % 10`** — The baseline for the result model is computed as `max(Counter(y_result % 10).values()) / len(y_result)`. This treats the units digit of the raw result integer as a proxy for the full label. If `y_result` stores 4-digit lottery numbers (e.g., 3842), the modulo extracts the units digit (2), which is one of 10 classes — plausible, but not the same distribution as the actual `y_result` classes. Verify that `y_result` values are single-digit (0–9) labels and not raw lottery numbers. If they are raw numbers, the baseline is misleading.

### Index alignment fix and series encoding consistency

In both `main.py` and `prediction.py`, the `generar_features()` call followed by `.replace([np.inf, -np.inf], np.nan).dropna()` can drop rows from the middle of the sorted dataframe, not just from the tail. The old `.tail(len(X_df))` always cut from the end, so if NaNs were scattered internally the target vector and feature matrix would silently reference different draws. The `.loc[X_df.index]` fix ties the target to the exact surviving rows. This is the most impactful behavioral correction in the batch.

The series encoding fix removes the data-order dependency. The old `astype("category").cat.codes` assigned codes based on which signs appeared in the current slice, in the order they first appeared. A model trained on a slice where `ARI` happened to appear first would assign code `0` to `ARI`, but a different slice might assign code `0` to `CAN`. Predictions would be silently wrong when model and prediction dataset used different implicit mappings. The fixed encoding pins `ARI=0, TAU=1, ...` everywhere, and the `sign_mapping` key in the saved payload makes this explicit.

### Chronological split and baseline accuracy

The test set in `_evaluar_individuo` is now always the most recent 20% of draws (confirmed by `split_idx = int(n * (1 - test_size))`). This is the correct evaluation methodology for time-series prediction — testing on future data relative to training. The `train_test_split` import is gone.

The baseline accuracy calculation computes the majority-class frequency for `y_series` correctly: `max(Counter(y_series).values()) / len(y_series)`. The `y_result % 10` approximation for `baseline_result` is the one questionable element — see Issues.

### Fixup commit: excel_updater restoration

The fixup commit (`1a8aec8`) restores `excel_updater.py`, which ended mid-file in the base branch (literal truncation: `logger = get_logger(_` with no newline). The restored version implements `actualizar_excel_incremental()`, an incremental scrape-and-append function that reads the last date from the existing Excel file and fetches only new results. It uses `settings.LOTTERIES`, `settings.CLAVES_UNICAS`, and `SuperAstroScraper` — all consistent with the rest of the changes. The `get_logger` alias added to `logger.py` in the same commit is the missing symbol that `excel_updater.py` was already trying to import.

### Documentation accuracy

`ARCHITECTURE.md` now names `synchronize_database()` in the data flow diagram (replacing the stale `sincronizar_con_neon()`), and correctly annotates legacy files as `# presente — uso interno / legacy`. The ASTRO LUNA-only model note appears in both the directory tree and the "Modelos guardados" section. `README.md` adds the `⚠️ Aviso importante` section prominently after the title. The Docker Compose service names in `README.md` (`sync`, `prediction`) don't match the plan's names (`lottery-system`, `lottery-scheduler`) and can't be validated — no `docker-compose.yml` exists in the repo.
